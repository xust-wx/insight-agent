# ADR-004 · 语义层与检索策略：全量核心 Schema 常驻 + 混合检索与干扰表压测

- 状态：已接受（2026-11-24）
- 关联评审项：`S0_review.md` P1-2

## 背景
Olist 清洗后仅有 **9 张核心业务表、约 50 个字段**，精简 DDL + 注释仅占 ~1,800 tokens；若强行对 9 张表做向量 Top-K 召回，不仅没有节省多少 Token，反而引入“漏召回关联表”的人为错误。但真实企业数仓往往有数十至上百张表，如何在不造假的前提下同时兼顾实用性与架构说服力？

## 决策
采用**双模式分层检索设计**：
1. **默认生产模式（9 表场景）**：
   - `olist_clean` 9 张核心表的精简 Schema 摘要**常驻注入上下文**（保证 100% 表覆盖，还能命中 LLM Prompt Cache）。
   - **混合检索（PostgreSQL `tsvector` BM25 + `pgvector` 余弦相似度，RRF 融合）** 专门用于检索：
     - 指标口径模板与不兼容维度规则（`03_metrics_glossary.yaml`）；
     - 历史验证过的 Few-shot SQL 样例；
     - 用户确认过的口径偏好记忆。
2. **数仓扩展压测模式（`include_distractors=True`，S4 专项评测）**：
   - 在 `olist_distractor` Schema 下自动生成 30 张逼真的电商周边业务表（如仓储批次、客服工单、财务科目、员工排班、优惠券批次等）。
   - 在 39 张表总规模下开启表级混合召回（Top-8 表），在 `06_eval_report.md` 中实测汇报 `Recall@8`、Token 节省比例与端到端准确率变化。

## 后果
- 诚实面对数据规模，避免过度设计导致小库准确率下降。
- 在 S4 中既有高准确率的实用表现，又有可复现的多表召回压测实验数据。
